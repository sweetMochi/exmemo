# Coding Agent 與技術債

> [!info] 來源
> YouTube 訪談（英文）· 精華剪輯，約 9.5 分鐘 · [影片連結](https://www.youtube.com/watch?v=b-i1JXYovPw)
> 文字稿：[[AI Coding 越來越強，為什麼 Code 反而更難維護？Coding Agent、技術債與程式碼品質的真相.txt]]
> 文字稿為片段剪輯，中間有跳段，部分上下文缺漏。

## 核心主張

> **"Do not mortgage your codebase in the hopes that in a year the model will come out that's smart enough to fix all your problems."**
> 別拿 codebase 去抵押，賭一年後會出一個聰明到能收拾一切的模型。

Coding agent 越來越強，但放任它在同一個 codebase 裡連續工作，程式碼品質會**持續惡化**。解法不是等更強的模型，而是**人在迴路中（human in the loop）、做好規劃、小步交付、一次專注一件事**。

## 1. Benchmark 分數 ≠ 真實開發

- 「某模型 SWE-bench 分數拿 95%，所以 coding 一定沒問題」—— 寫程式不是這樣
- 這類 benchmark 的任務**小而明確**（讓測試通過），而且**一開始就把整個問題交給模型**
- 真實軟體是**逐步長出來的**：需求一個個進來，沒人一開始就知道全貌

### SlopCodeBench：模擬「一路加功能」

```
Greenfield 建立專案 → 加功能 A → 加功能 B → ...（每題 3～10 個 checkpoint）
```

- 模型在**不知道全貌**的情況下，在同一個 codebase 上**無人監督**地持續開發
- 結果：所有模型的**失敗測試數都隨時間上升**，程式碼越來越爛
- 講者提到 GPT 5.5 Codex 五月的跑分約 **15%**

## 2. 規劃：逐層消除失敗模式

- Spec 和 plan 無法涵蓋一切，**真正的 source of truth 是程式碼**
- 規劃可以**先排除 agent「可能」走錯的路**
- 我們從高空俯看的方式理解：

| 層級       | 形式    | 排除的錯誤解法        |
| -------- | ----- | -------------- |
| 25,000 呎 | 一頁式概要 | 約 50%          |
| 10,000 呎 | 更細的設計 | 再排除約 80%       |
| 產出程式碼    | —     | 重工只需 **0～10%** |

- 對比：大型 agent PR 若想一次生成（one-shot），經常需要 **25～75% 重工**
- 實際上沒人只說一句「Claude，去做這件事」，大家都是**來回協作**
- 講者認為，**寫好 design doc / prompt 的能力**，會和 code review 一樣重要，甚至更重要

## 3. 現實的生產力目標：2～4 倍

- 每位工程師快 **2～4 倍**，對人類社會的影響就已經是革命性的
- 很多人追求 100 倍效率，還甚至說出「以後我們不再需要工程師」，結果**連 2～4 倍的成效都無法達標**
- 建議：先穩穩做到 2～3 倍，再在此基礎上**疊加**下一個 2～3 倍
- 可以拋棄不必要的傳統，但**把整套工程實踐全部丟掉、從零重建是不實際的**

## 4. 人的品味（taste）仍不可取代

- 資深工程師**被爛架構傷害過**：他在凌晨三點救火時悲憤說到：「不可以讓任何人 merge 這種寫法」
- 這種品味讓人能說「不，我不要這樣做，要那樣」
- 目前還沒辦法把這種品味放進模型，**所以現在得由人來做**

## 5. 夜間「清潔機器人」：像恆溫器一樣

- 講者團隊約 **10% 的 PR** 由夜間執行的 janitor bot 產生並 merge
- 原理像**恆溫器**：定義 codebase 的**理想終態** → 偵測差距 → 自動往該方向推進
- 每天早上收到幾個不同面向的清理 PR：
	- 重構
	- 修正 React Doctor 規則
	- 把 endpoint 從舊框架遷移到新框架
- 關鍵：**每個 PR 都很小、好消化**——PR 太大就永遠不會被 merge
- 只有少數工作適合讓 agent 整晚**爬坡優化（hill climbing）**；講者不想一早醒來面對一萬行程式碼

## 6. 少做幾件事，反而更快

- 反模式：規劃 10 件事、整晚丟出去 → 早上花 4 小時 review → 幾天後只上線 2 件，其他還卡著
- 建議：**規劃 2 件、現在開始、邊做邊看、今天就上線**，然後再來 2 件
- 這是工程（和所有工作）一直以來的道理：**降低在製品數量（WIP），端到端交付反而更快**
- 平行處理時也要有「**最重要的那件事**」：
	- 它一解除阻塞，就算正在寫 prompt 也要立刻切回去
	- 目標是**讓那件事上線**，其他工作只是等待時的填空

> [!quote] 拉霸機 vs. 撲克
> 同時跑六個 agent 像在賭場猛拉拉霸機；一次跑一個 agent 像打撲克——**一次只玩一手，專注**。講者很想看腦部掃描研究比較兩者。

## 總結

| 迷思                             | 講者觀點                          |
| ------------------------------ | ----------------------------- |
| AI Benchmark 高分 = coding 問題已解決 | 真實開發是逐步加功能，agent 無人監督時品質會持續下滑 |
| 未來的模型會幫我收拾技術債                  | 別抵押你的 codebase，現在就要維護品質       |
| 一句 prompt 一次生成                 | 逐層規劃，把重工從 25～75% 降到 0～10%     |
| 目標是 10 倍、100 倍效率               | 先穩定 2～4 倍，再疊加                 |
| 平行越多越有效率                       | 減少製作出更多東西，聚焦最重要的一件事           |
| 自動化就要大量產出                      | 自動化的 PR 要小，否則沒人看也沒人 merge     |

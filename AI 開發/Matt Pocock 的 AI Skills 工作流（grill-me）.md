# Matt Pocock 的 AI Skills 工作流（grill-me）

> [!info] 來源
> YouTube 影片 · 約 20 分鐘 · [影片連結](https://www.youtube.com/watch?v=aR97E7aKEgg)
> 文字稿：[[700 萬人下載的 grill-me，Matt Pocock 到底寫了什麼？.txt]]

## 背景

- **Matt Pocock**：TypeScript 領域的頂尖專家與講師
- 他把自己的 AI 開發工作流開源成一整套 skill，GitHub 超過 16 萬星、下載 700 萬次
- 目標：**控制 AI 的隨機性**（AI 是充滿隨機性的黑盒子）
- 他認為 Get Shit Done、Spec-Kit、Superpowers 這類框架**想接管整個開發流程**：流程繁瑣且沒有彈性，前面一步錯了，錯誤會一路傳到後面，要改就得整條重跑
- 他的做法相反：每個 skill **小、好改、能自由組合**（模組化）

## 主要工作流

```
grill-me → to-spec → to-tickets → implement（TDD）→ code review
                                        ↑
         improve-codebase-architecture（定期保養）
```

### 1. grill-me：讓 AI 反過來拷問你

整個 skill 只有**五行**：

1. 在計畫達成共識之前，盡可能刨根就底地問
2. 像畫心智圖一樣順著決策樹延伸，把每個決定引發的連鎖反應一路問到底
3. **一次只問一個問題**，並**附上建議答案**
4. 設計達成共識前，**不准寫程式**

> [!note] 為什麼需要
> 寫程式就是連續做幾百個小決定（防呆、斷線、極端資料…）。Vibe Coding 等於把這些決定全交給 AI，AI 為了討好你，常會寫出難維護的架構。
> grill-me 把**找漏洞**交給 AI，**拍板定案**留給人類，讓人類維持架構師的位置。

### 2. to-spec：把共識寫成規格書

- 對話一關掉 AI 就立刻失憶，所以要把共識存成規格
- **禁止在規格裡引用或寫程式碼**
	- 程式碼最容易變動，文件永遠跟不上
	- 規格裡有過期的程式碼，下次 AI 照規格改功能時會被誤導
	- 規格只寫「這個功能要解決什麼問題」

### 3. to-tickets：用功能切任務（垂直切分）

|       | AI 預設的切法（水平）      | to-tickets 的切法（垂直） |
| ----- | ----------------- | ------------------ |
| 依據    | 技術層：資料庫 → 後端 → 前端 | 使用者功能：登入、加入購物車…    |
| 每個任務  | 只做一層              | 包含 DB＋邏輯＋畫面        |
| 何時能測試 | 前端完成後才能測          | 每個任務做完就能在瀏覽器測      |
| 錯誤發現  | 很晚，前面的工可能白做       | 很早                 |

- 會排出任務順序，**互不相依的任務可以平行交給多個 AI**

### 4. implement：用 TDD 實作

- 依任務清單寫 code，過程以 **TDD（測試驅動開發）** 引導，完成後自動呼叫 Code Review
- **為什麼 AI 需要 TDD**：AI 會「作弊」。先寫程式再補測試時，若邏輯錯了（滿千折 100 寫成折 200），它會寫一個配合錯誤邏輯的測試讓它通過
- TDD 的順序：**先寫測試 → 紅燈（失敗）→ 寫程式 → 綠燈（通過）**，先把規則定死，AI 就沒辦法用假測試交差

### 5. Code Review：開新 session 審查

- 開一個**全新的 session**，避免被寫程式時的上下文干擾
- 不是一句「幫我檢查 bug」，而是把《Refactoring》書中的 **12 種 code smell** 寫成檢查清單，例如：

| Code Smell | 症狀 | 處理 |
|---|---|---|
| **Shotgun Surgery** | 改一個地方要動十幾個檔案 | 把散落的修改集中 |
| **Feature Envy** | 訂單邏輯一直去拿庫存那邊的資料 | 把邏輯搬到它該在的地方 |
| **Data Clumps** | 姓名、電話、地址總是一起出現 | 打包成一個物件（如「聯絡人」） |

## writing-great-skills：怎麼寫精簡的 skill

| 原則              | 說明                                               |
| --------------- | ------------------------------------------------ |
| **修剪（Pruning）** | 刪掉廢話、讓 AI 分心的文字，以及模型本來就會做的指令。每多一句廢話，AI 就多一分分心的可能 |
| **指引詞**         | 用 AI 訓練資料裡就有的經典術語（如 Data Clumps），一個詞取代一百字的解釋     |
| **完成標準**        | 給 AI 一個明確的終點                                     |

## improve-codebase-architecture：對抗淺模組

- **問題**：AI 沒有大局觀，一次只看幾個檔案，容易寫出很多**淺模組（shallow module）**，邏輯過度碎片化
	- 比喻：房間分得很乾淨，但房子沒有大門，每個房間都要從不同的窗戶或煙囪進去
	- 例：結帳被拆成「計算折扣、驗證信用卡、建立訂單、扣庫存、寄信」五個模組，主程式要自己串起所有資料傳遞
	- AI 的 context window 有限，修 bug 時得在多個檔案間跳轉，超出記憶就會開始瞎猜
- **深模組（deep module）**：一個簡單的介面（如 `processCheckout()`），把複雜的細節藏在裡面
	- 不是把所有程式碼塞進一個檔案，而是**介面簡單、內部複雜**
	- **局部性高**：出問題時 AI 只要讀這一個模組
- **刪除測試（deletion test）**：想像拔掉某個模組，讓呼叫端自己處理
	- 複雜度全部炸回呼叫端 → 這是有在做事的深模組
	- 程式反而變清爽 → 這是多餘的空殼，應該移除
- **用法**：每隔幾天跑一次，會產生 **HTML 診斷報告**和前後架構對比圖，挑一個最急的建議請 AI 重構

## 其他 skill

- **grill-with-docs**：grill-me 的進化版，Matt 自己比較常用
	- grill-me 每次都得重新熟悉專案，而且專有名詞的定義、當初為什麼這樣決定，都無法從程式碼查到
	- 拷問時順便把**專有名詞和重要決策寫成文件**，下次一開場就能直接問到重點
- repo 裡還有**三個寫作用的 skill**（影片未展開）

## 與 Superpowers 比較

| | Superpowers | Matt Pocock skills |
|---|---|---|
| 理念 | 完整、寫死的工作流（9 個步驟） | 極簡、模組化，一個 skill 解決一個問題 |
| 比喻 | 組好的自動化生產線 | 隨插即用的樂高積木 |
| 適合 | 模型較弱、容易偏題的時期（保母級防呆） | 能力強的模型 |
| 彈性 | 需從頭走完設計 → 計畫 → 執行 | 可從任一步開始，例如拿現成規格直接 to-tickets |
| 產出文件 | 為自己的下一步量身打造，別人難接手 | 通用，容易接手 |

## 結論

Matt 靠深厚的軟體工程底子駕馭 AI，用在兩個地方：

1. **架構**：把深模組、code smell 等經過驗證的老方法寫進 skill，規範 AI 的行為
2. **溝通**：用專業術語當 prompt，精準又精簡，讓 AI 沒有發散的空間

> [!tip] 重點
> 有了 AI 仍要在自己的專業領域精進。**只有成為領域專家，才能真正控制好 AI。**

| AI 的問題 | 對應方法 |
|---|---|
| 自己亂猜，做出來的跟你想的不一樣 | grill-me、to-spec 先逼出細節 |
| 寫出無法測試的半成品 | to-tickets 垂直切分 |
| 會作弊 | TDD |
| 記憶有限 | 精簡的指引詞＋深模組 |

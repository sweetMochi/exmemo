# 為什麼手寫程式碼反而是優勢

> [!info] 來源
> YouTube 影片（英文）· 約 17.5 分鐘 · 講者正在用 Rust＋FFmpeg 開發影片剪輯軟體 Kiru
> 文字稿：[[Writing code by hand is now an advantage.txt]]

## 核心主張

網路上越來越多人說「AI agent 時代手寫程式是浪費時間」。講者認為相反：**手寫程式不是浪費，而是優勢**。正因為越來越多人完全不寫程式，有手寫經驗的人反而更突出，也更會用 agent。

## 思考實驗：你會雇用哪位候選人？

情境：要找人接手一個用 Rust＋FFmpeg 寫的影片剪輯軟體，三位候選人最近都用 Rust 做過影片播放器。

| 候選人 | 背景 | 播放器怎麼做的 |
|---|---|---|
| **A** | 從 Vibe Coding 時代就全面採用 agent，2025 年起沒手寫過一行程式，從沒手寫過 Rust／FFmpeg | 全部用 Claude Code、Codex 等 agent 完成 |
| **B** | Agent 前手寫 Rust 三年，最近才開始用 agent | 大部分手寫（Rust＋iced），但播放器核心用現成 crate |
| **C** | 日常也用 agent，但會刻意找機會手寫，特別是為了學習 | **親手實作媒體引擎**（ffmpeg-sys），卡住時才問 AI |

講者會選 **C**：只有 C 親手做過關鍵元件，理解影片剪輯會碰到的核心概念。

> [!note] 講者自己的經歷：從 A 變成 C
> 他的影片剪輯軟體媒體引擎原本全由 agent 寫成，**能跑但不正確**，面對各種媒體檔案一直出錯。因為有知識缺口，他**無法判斷 agent 給的新解法是否正確**。
> 於是他手寫一個簡單的媒體管線來學 FFmpeg（過程中也用 AI 輔助）。結果不只更懂媒體播放，重建引擎時也**更會用 agent**。

## 問題在哪：agent 讓人跳過學習

用 agent 也能學習，但很容易**跳過真正讓人學會的情境**：遇到問題、掙扎、在找解法的過程中有所發現。所以他刻意挑「投資報酬率最高」的地方手寫，而不是全部手寫。

## 值得手寫的五個場合

### 1. 學新的程式語言

- 方法很傳統：拿一本書，照著手寫範例；卡住或需要不同解釋時再問 LLM
- 最大收穫：**審查 AI 程式碼時更能聞出 code smell**
- 例子：**Boolean creep（布林蔓延）**——agent 傾向一直新增布林值，而不是用定義良好的 enum 加一個 variant

```rust
// agent 寫的：側邊欄目前在哪個分頁，用一堆 bool 表示
struct SidebarState { home: bool, projects: bool, settings: bool }

// 手寫過的人會這樣寫：互斥狀態用 enum
enum SidebarTab { Home, Projects, Settings }
```

### 2. 學習依賴套件

- 有些套件有重大「眉角」，例如跨平台音訊套件 **CPAL**：
	- 它提供一條**即時音訊執行緒（real-time audio thread）**，必須跑得極快，否則會有爆音、跳音
	- Agent 為了執行緒安全用了 **mutex** → 可能阻塞執行緒、掉樣本，即時音訊的大忌
	- 他先在測試專案手寫過，所以 review 時馬上看出問題，知道該用**即時 ring buffer**
- FFmpeg、GPUI 文件都很差 → 這時 **agent 反而很好用**：用提問補足文件缺口
- 學會依賴套件後，和 agent 協作形成**正向循環**

### 3. 高層架構設計（"Feel the air"）

- AI 傾向走**最短路徑**產出能跑的程式，放任不管會讓 codebase 變成一團亂
- 典故：《星際效應》中 Cooper 降落米勒星球時拒絕電腦輔助，要「感受空氣」的回饋
- 手寫高層設計，能在交給機器前**先感受到設計的阻力**
- 他重建媒體引擎的做法：

```
定義 trait 與高層型別 → 方法／函式簽名 → 內容用 unimplemented!() 佔位
                                              ↓
                       可以編譯，也是給 agent 的「這裡要實作」標記
```

- 結果：引擎更強、跨平台結果一致，之後加入圖片、特效、轉場容易很多

### 4. Codebase 理解力

- 講者認為這是**未來開發者最大的問題**
- 以前在 codebase 待夠久就有心智模型，bug 一出現直覺就知道在哪；用 agent 做的專案，**就算從零開始、每個變更都 review，理解度也差很多**
- 整個產業正處於危險處境：很多專案**連作者自己都不完全理解程式碼**
- 他的做法：**先手寫想理解的部分 → 再交給 agent 改進，或把同樣模式套用到其他地方**（比一次生成慢，但先建立了心智模型）
- 問 agent 也能幫助理解，但會幻覺。因此以下領域**只手寫**：
	- 金流
	- 使用者驗證
	- 其他出 bug 會造成災難的地方
- 諷刺的是，這些地方他**最需要 agent 或工具做對抗式審查（adversarial review）**

### 5. 樂趣（講者認為最重要）

- 用 agent 做產品，遠不如手寫程式那樣有腦力刺激
- 與其哀悼「手寫程式已死」，不如重新擁抱它
- **把時間花在自己喜歡的事情上，就不算浪費**

## 總結

| 手寫的場合 | 帶來的好處 | AI 扮演的角色 |
|---|---|---|
| 學語言 | 審查時抓得到 code smell（如 boolean creep） | 卡住時解釋 |
| 學依賴套件 | 知道隱藏限制（如即時執行緒不能用 mutex） | 補足爛文件 |
| 高層架構 | 感受設計阻力，避免最短路徑造成的混亂 | 依 `unimplemented!()` 標記實作 |
| 想理解的程式碼 | 建立心智模型 | 改進、擴散相同模式 |
| 關鍵程式碼（金流、驗證） | 確保正確性 | 對抗式審查 |

> [!tip] 重點
> 手寫不是要取代 agent，而是**補上知識缺口，讓你有能力判斷 agent 的產出對不對**。和 [[Matt Pocock 的 AI Skills 工作流（grill-me）]] 的結論一致：**成為領域專家，才能真正駕馭 AI。**
